# TableShift-derived diabetes domain pilot (2026-10-20)

Source: [TableShift repository](https://github.com/mlfoundations/tableshift), inspected at commit `fca9429814703a07e3902d005d46563a207b7f0a`. Data: [UCI Diabetes 130-US Hospitals](https://archive.ics.uci.edu/dataset/296/diabetes+130-us+hospitals+for+years+1999-2008), CC BY 4.0. The downloaded archive is `data/raw/tableshift/dataset_diabetes.zip`, SHA-256 `66d9820c3bd5fd2abf7957bda2d9714b2de1e7bba1ac1f1ff8fa85e83c22cb33`; raw data is Git-ignored.

The upstream domain is `admission_source_id == 7` (emergency admission source) versus all other sources; target is `readmitted != NO` (any recorded readmission). Upstream prose about 30-day readmission is inconsistent with its implemented label. After its missing-race filter, there are 99,493 rows, 56,632 target-domain and 42,861 source-domain encounters. There are 6,300 patient IDs shared across domains. The published row splitter therefore risks patient overlap. Our primary protocol removes shared patients from source and group-splits by patient. It is **not an exact TableShift score**. The target domain is split into an unused OOD validation partition and final OOD test, both patient-disjoint. The 17 prespecified encounter features omit patient ID, admission-source ID and discharge disposition; this bounded feature subset also differs from the upstream task.

The archive SHA and row count are checked before fitting. Preprocessing is fit inside each expert's training pipeline. Model selection uses source selection Brier only, split conformal uses an independent source calibration partition, and ID/OOD labels are used only for final evaluation. OOD patient identifiers are used during curation solely to avoid entity overlap. The fixed seed is 264738. The 12,000-row source fit cap samples whole patients. Raw records and identifiers are not in JSON output.

Run with `./.venv/Scripts/trusttabx.exe natural-benchmark --max-fit-rows 12000 --output outputs/tableshift_diabetes_12000.json`. The JSON records split hashes, sizes, package versions, selection scores, fit/inference timing, memory and metrics. CPU-only, one model per fit, no tuning trials. The 3- and 5-expert decisions both charge the same shared five-model fit pool (5 total fits, 3 vs 5 selection candidates); this isolates candidate access at equal realized training cost, but it is not a deployment cost comparison of separate 3- and 5-model systems. Timings are local wall-clock measurements; Windows peak working set is recorded, not portable peak RSS.

An aggregate-only copy of the verified result is tracked at `reports/results/tableshift_diabetes_12000.json`; the raw archive remains ignored.
